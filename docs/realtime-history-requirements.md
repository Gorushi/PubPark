# 개발 요구사항: 실시간 주차 이력 수집기 및 수집 상태 요약

| 항목 | 내용 |
| --- | --- |
| 프로젝트 | PubPark |
| 작성일 | 2026-11-10 (Asia/Seoul) |
| 문서 버전 | 1.0 |
| 상태 | 구현 전 요구사항 초안 |
| 대상 | 백엔드 수집·저장·데이터 품질·상태 요약·앱 최신 현황 연동 |

이 문서는 개발할 동작과 완료 기준을 정의한다. 문서에 기술된 수집기·DB·명령·출력 예시는 구현 완료를 의미하지 않는다. 초기 기본값은 이 문서에 따라 구현하고, 조정 가능한 정책은 설정과 판정 버전으로 관리한다.

## 1. 목적과 배경

서울시 시영주차장의 시간대별 현황을 지속적으로 축적하여 향후 주차장별 도착 예상 시점의 잔여 주차면수를 예측할 수 있는 기반을 구축한다. 원본 제공 데이터의 오류·지연·누락을 식별하고 수집 시스템의 장애와 제공처 데이터 품질을 구분한다.

현재 구현은 월별 정적 정보·좌표 수집과 앱 요청 시 서울시 현황을 조회하는 API이다. 현재 API의 5분 캐시는 영구 이력 수집을 대체하지 않는다. 새 수집기는 앱 실행·사용자 검색과 독립적으로 동작해야 한다.

### 1.1 범위

- 서울시 GetParkingInfo의 실시간 주차 현황 주기 수집.
- 실행 회차, 고유 관측, 회차별 관측 확인 기록 저장.
- 중복 관측 처리, 수정 관측 보존, 품질 판정.
- 24시간·7일·전체 기간 수집 상태 요약과 JSON 출력.
- 수집한 최신 현황을 기존 앱 API에 연결.
- 실행·복구·백업·설정 문서와 자동 테스트.

### 1.2 제외 범위

- 예측 모델 학습·성능 보장·주차 가능 확률 산출.
- 관리자 웹 대시보드, 이메일·메신저 알림 발송.
- 과거 API 이력 소급 조회나 누락 기간의 임의 복원.
- 원본값 자동 보정, 보간값을 관측 원본으로 저장하는 작업.
- 월별 정적 정보·Geocoding 수집기의 대체.
- 관광버스 전용 주차장 및 버스 요금 관련 필드 수집.

## 2. 용어와 공통 원칙

| 용어 | 정의 |
| --- | --- |
| 예정 회차 | 수집 시스템의 운영 시작 이후 5분 단위로 예정된 실행 구간 |
| 실행 회차 | 실제로 실행을 시작한 수집 작업 |
| 원본 관측 | 제공처의 특정 주차장 갱신 시각 및 상태·측정값 |

| 수정 관측 | 동일 주차장·동일 원본 시각에 다른 값이 반환된 관측 |
| 확인 기록 | 특정 실행 회차에서 특정 관측이 반환됐다는 기록 |

| 기본 학습 후보 | 품질 검사 통과 상태이며 실제 학습 적합성은 별도 검증이 필요한 관측 |

필수 원칙:

1. 알 수 없음과 실제 0대를 구분한다.
2. 수집 시각을 원본 갱신 시각으로 대체하지 않는다.
3. 현재 API를 나중에 호출해 받은 값으로 과거 누락 구간을 채우지 않는다.
4. 원본 측정값과 계산·판정 결과를 분리한다.
5. 모든 비율에 분자·분모·집계 기간을 명시한다.
6. 시각은 시간대가 있는 값으로 처리한다. 저장은 UTC, 일정·표시는 Asia/Seoul 기준을 기본으로 한다. 원본 문자열도 보존한다.

## 3. 수집 대상 요구사항

### FR-01. 대상 식별과 제외

- 제공처 코드는 seoul, 주차장 ID는 PKLT_CD 문자열로 관리한다.
- 관광버스 전용 제외 기준은 기존 검색 API와 공통 함수로 관리한다.
- 운영구분명에 버스전용이 있거나 이름에 관광버스전용이 있으면 제외한다. 공백은 정규화한다.
- 단순히 BUS_ 요금 필드가 있다는 이유로 일반 주차장을 제외하지 않는다.
- 미연계 주차장도 상태 분석을 위해 기록한다.
- 좌표가 미확정이어도 이력을 수집한다. 지도 노출 가능 여부와 이력 수집 가능 여부는 분리한다.
- 새 ID는 관측된 시점부터 대상으로 등록한다. 정적 목록에 없다는 이유로 버리지 않는다.
- 조회에서 사라진 주차장을 즉시 폐쇄·삭제로 확정하지 않는다. 반환 누락으로 기록한다.
- 정적 월별 갱신으로 이름·구분 등이 바뀌어도 과거 대상·제외 이력을 소급 변경하지 않는다.

### FR-02. 대상 집합 기록

- 각 회차의 예상 대상과 실제 반환 대상을 구분한다.
- 예상 대상은 직전 성공 전체 조회에서 확인된 비제외 주차장 목록을 기준으로 하되, 현재 회차에서 새로 발견된 ID도 기록한다.
- 최초 실행처럼 예상 대상이 없으면 그 상태를 명시한다. 추측한 분모를 만들지 않는다.
- 신규·제외·미반환 주차장 수와 ID 목록을 진단 가능하게 보존한다.
- 관광버스 제외에는 제외 사유를 남기되 불필요한 전체 원본 필드는 저장하지 않는다.

## 4. 실행과 스케줄 요구사항

### FR-03. 기본 주기

- 한국시간 매시 00·05·10·15·20·25·30·35·40·45·50·55분에 실행한다.
- 완료 후 5분 대기하는 방식으로 일정이 계속 밀리지 않게 한다.
- 앱이 종료돼 있어도 실행된다.
- 실행 중인 회차가 있으면 중복 수집하지 않는다. 후속 실행은 중복 방지 상태로 기록한다.
- 이전 수집이 5분을 초과하면 해당 사실을 기록하며 겹치는 작업을 시작하지 않는다.

### FR-04. 시작·재시작·누락 회차

- 최초 시작 시 현재 현황을 한 번 수집하고 다음 정규 경계부터 실행한다.
- 재시작 시 미완료 실행을 interrupted로 식별하고 새 작업을 시작할 수 있어야 한다.
- 놓친 회차를 과거 관측처럼 생성하거나 밀린 수만큼 API를 연속 호출하지 않는다.
- 예정됐지만 실행되지 않은 구간은 누락 회차로 계산한다.
- 운영 시작 시각, 일정 변경, 명시적 중지·재개 시각을 기록한다.
- 중지 상태와 예기치 않은 실행 공백은 요약에서 구분한다. 중지 기간을 조용히 분모에서 없애지 않는다.
- 시스템 시각 변경·시각 역행이 있어도 동일 예정 회차를 중복 처리하지 않는다.

### FR-05. 실행 환경

- Python CLI와 외부 스케줄러로 실행할 수 있는 일회 실행 진입점을 제공한다.
- 개발 PC에서는 Windows 작업 스케줄러 등으로 등록하고 실행 계정·작업 경로·다음 실행 시각을 확인할 수 있어야 한다.
- 주기 실행 방식은 프로세스 내부 스케줄러 또는 OS 스케줄러 중 하나를 주 운영 방식으로 명시한다. 두 방식을 동시에 등록하지 않는다.
- 24시간 축적은 상시 가동 서버를 운영 조건으로 한다. 개발 PC 종료·절전·로그아웃으로 생긴 공백은 복구 가능하다고 표현하지 않는다.
- import만으로 네트워크·파일 쓰기·스케줄 등록을 수행하지 않는다.

## 5. API 요청과 장애 처리

### FR-06. 전체 페이지 조회

- 서울시 제공 건수를 기준으로 페이지를 나누어 조회한다. 페이지 크기는 제공처 허용 범위를 준수한다.
- HTTP 상태와 응답 본문의 API 결과 코드를 모두 검사한다.
- 전체 건수, 반환 행 수, 중복 ID, 페이지 누락, 응답 형식을 검증한다.
- 수집 중 전체 건수가 바뀌거나 페이지 간 ID 중복이 발생하면 불완전한 전체 조회임을 명시한다.
- 한 페이지 실패가 전체 수집 루프를 무한히 붙잡지 않도록 한다.

### FR-07. 재시도 정책

| 상황 | 초기 처리 정책 |
| --- | --- |
| 연결 실패·타임아웃·일시적 5xx | 최초 포함 최대 3회, 재시도 전 2초·4초 대기 |
| 인증·권한 오류 | 해당 회차 중단, 즉시 재시도하지 않음 |
| 한도 초과·429 | Retry-After가 있으면 기록·준수, 즉시 반복 호출하지 않음 |
| 잘못된 요청·지속적 응답 형식 오류 | 오류 유형을 기록하고 해당 페이지 실패 처리 |
| DB 오류 | 성공 처리 금지, 비정상 종료 코드와 로컬 오류 로그 남김 |

- 초기 연결 제한 시간 10초, 읽기 제한 시간 30초를 설정으로 제공한다.
- 재시도·페이지 조회를 포함한 한 실행의 시간 예산은 초기 240초로 둔다. 초과하면 확보한 데이터의 상태를 기록하고 종료한다.
- 실행별 네트워크 시도 횟수와 최종 실패 유형을 기록한다.
- 키가 포함된 URL, 원본 예외 문자열, 요청 헤더를 그대로 로그에 남기지 않는다.

### FR-08. 성공 상태

| 상태 | 판정 |
| --- | --- |
| success | 전체 페이지와 건수·ID 검증을 통과하고 DB 저장 완료 |
| partial_success | 일부 유효 관측을 저장했지만 페이지·건수·대상 검증이 불완전 |
| failed | usable한 응답을 확보하지 못했거나 저장하지 못함 |
| skipped_overlap | 다른 실행과 겹쳐 수집을 시작하지 않음 |
| interrupted | 시작 기록은 있으나 정상 종료되지 않은 과거 실행 |

- 회차 success는 데이터 품질 100%를 의미하지 않는다. 미연계·초과 데이터도 정상 수신됐다면 품질 상태와 함께 보존한다.
- 부분 성공 시 확보한 관측은 저장하되, 미반환 주차장의 최신 정보를 삭제하거나 0으로 바꾸지 않는다.
- 원본 시각이 더 오래된 응답은 이력에 보존할 수 있지만 최신 현황을 무조건 과거로 되돌리지 않는다.

## 6. 데이터 저장 요구사항

### DR-01. 기본 저장소

- 초기 DB 파일: backend/data/parking_history.sqlite3.
- 기존 seoul_parking_static.sqlite3와 분리한다.
- SQLite 외래키, 트랜잭션, WAL 모드, busy timeout을 설정한다.
- PUBPARK_DATA_DIR에 따라 경로를 결정하며 개인 PC 절대경로를 코드에 고정하지 않는다.
- 스키마 버전과 마이그레이션 절차를 제공한다. 기존 이력이 있으면 초기화하지 않는다.
- 초기 버전은 자동 이력 삭제를 수행하지 않는다. 삭제·압축 정책은 별도 결정한다.

### DR-02. 논리 테이블

실제 테이블·필드 이름은 구현 시 정할 수 있으나 아래 의미와 관계는 보존해야 한다.

#### A. collection_runs — 수집 회차

| 필드 | 요구 의미 |
| --- | --- |
| run_id | 고유 실행 ID |
| scheduled_at | 예정 시각 |
| started_at, finished_at | 실제 시작·종료 시각 |
| status | 회차 상태 |
| source, collector_version | 제공처·수집 코드 버전 |
| expected_count, reported_total, returned_count | 예상 대상·제공처 전체 건수·반환 건수 |
| target_count, excluded_count, missing_count | 대상·제외·미반환 건수 |
| new_observation_count, duplicate_count, correction_count | 신규·반복·수정 건수 |
| page_count, failed_page_count, request_attempts | 페이지·재시도 진단 |
| error_category | 정규화한 오류 유형, 비밀정보 제외 |

운영 일정과 비교해 누락 회차를 계산할 수 있어야 한다. 실제로 실행하지 않은 회차를 가짜 실행 레코드로 만들 필요는 없다.

#### B. parking_observations — 고유 관측

| 필드 | 요구 의미 |
| --- | --- |
| observation_id | 관측 ID |
| source, parking_lot_id | 제공처·주차장 식별자 |
| source_updated_at_raw | 원본 시각 문자열 |
| source_updated_at | 해석한 원본 시각, 실패 시 NULL |
| occupied_raw, total_raw, linked_raw | 필수 측정값 원본 |
| occupied_spaces, total_spaces | 검증·변환한 숫자, 실패 시 NULL |
| linked | 연계 여부, 알 수 없으면 NULL |
| available_spaces | 범위·연계·형식 등 기본 검사 통과 시의 계산값 |
| payload_fingerprint | 측정값·연계·원본 시각을 정규화한 해시 |
| revision, supersedes_id | 수정 관측의 관계 |
| first_seen_at | 최초 수신 시각 |

원본에는 이력에 필요한 필드만 포함한다. BUS_ 요금·불필요한 개인정보·키는 저장하지 않는다. 이름·주소·좌표는 정적 데이터와 연계하되 대상 판정에 사용한 구분·이름은 추적 가능해야 한다.

#### C. observation_receipts — 회차별 확인 및 품질 판정

| 필드 | 요구 의미 |
| --- | --- |
| run_id, parking_lot_id, observation_id | 회차·주차장·관측 연결 |
| collected_at | 해당 응답 수신 시각 |
| source_page | 원본 응답 페이지 |
| receipt_kind | 신규·반복·수정 확인 |
| freshness_seconds | 수신 시점의 원본 데이터 나이 |
| quality_flags | 복수 품질 상태 |
| eligible_for_training | 해당 판정 기준의 기본 학습 후보 여부 |
| quality_policy_version | 품질 기준 버전 |

같은 원본 관측도 확인 시점에 따라 정상 또는 지연이 될 수 있다. 따라서 지연 여부 등 수신 시각 의존 판정을 고유 관측 하나의 상태로 고정하지 않는다. 재판정 결과를 만들더라도 당시 판정과 구분한다.

#### D. collection_target_history / operation_history — 대상·운영 이력

- 주차장별 최초 확인, 포함·제외 변경, 사유와 적용 시점을 보존한다.
- 수집 운영 시작, 일정 변경, 중지·재개 이력을 보존한다.
- 기간별 예상 회차와 주차장별 응답률 분모를 재현할 수 있어야 한다.

### DR-03. 저장 원자성과 읽기

- 고유 관측, 확인 기록, 회차의 결과 건수를 일관된 트랜잭션으로 확정한다.
- 네트워크 대기 전체 시간 동안 DB 쓰기 잠금을 유지하지 않는다.
- 앱·요약 조회가 진행 중이어도 수집이 동작해야 한다.
- DB 쓰기 실패 시 실제 저장되지 않은 관측을 저장 완료 건수에 포함하지 않는다.
- 프로세스 종료로 남은 시작 기록은 다음 실행에서 식별 가능해야 한다.
- 최신 조회와 기간별 요약을 위해 주차장·원본 시각·수집 시각·예정 회차에 적절한 인덱스를 둔다.

## 7. 중복과 수정 관측

### FR-09. 중복 판정

| 입력 상황 | 처리 |
| --- | --- |
| 같은 ID·같은 원본 시각·같은 측정값/연계 상태 | 고유 관측 재사용, 새 회차 확인 기록 추가 |
| 같은 ID·같은 원본 시각·다른 측정값/연계 상태 | 수정 관측 새로 저장, 이전 버전 보존 |
| 같은 ID·다른 원본 시각·같은 값 | 새로운 고유 관측 |
| 원본 시각 누락 | 누락 상태 보존, 수집 시각으로 대체하지 않음 |
| 동일 회차 재실행 | 해당 회차·주차장 확인 기록이 중복 증가하지 않도록 보장 |

- 해시는 JSON 키 순서나 의미 없는 숫자 표현 차이에 영향을 받지 않도록 정규화한다. 해석 불가능한 원본 값은 손실 없이 구분한다.
- 원본 시각이 없는 행은 동일 값이라도 서로 다른 시점의 원본 관측인지 확정할 수 없다. 회차별 관측을 유지하고 기본 학습에서는 제외한다.
- 같은 페이지의 중복 ID와 페이지 간 중복 ID는 응답 이상으로 기록한다. 두 행을 조용히 덮어쓰지 않는다.
- 반복 확인 횟수를 신규 관측 수나 학습 표본 수로 계산하지 않는다.

## 8. 데이터 품질 요구사항

### FR-10. 초기 판정 규칙

| 플래그 | 조건 | 기본 학습 후보 |
| --- | --- | --- |
| unlinked | 제공처가 미연계로 표시 | 제외 |
| missing_value | 필수 측정값 누락 | 제외 |
| invalid_number | 숫자 해석 실패·대수의 소수값 | 제외 |
| invalid_capacity | 총면수 ≤ 0 | 제외 |
| invalid_occupied | 주차 차량수 < 0 | 제외 |
| over_capacity | 주차 차량수 > 총면수 | 제외 |
| missing_timestamp | 원본 시각 없음 | 제외 |
| invalid_timestamp | 원본 시각 해석 실패 | 제외 |
| stale | 수집 시각 대비 원본 시각이 20분 초과 과거 | 제외 |
| future_timestamp | 원본 시각이 수집 시각보다 5분 초과 미래 | 제외 |
| timestamp_regression | 이전에 확인한 최대 원본 시각보다 과거 | 검토 전 제외 |
| capacity_changed | 이전 관측 대비 총면수 변경 | 단독 사유로 제외하지 않음 |
| abrupt_change | 변화량 기준 초과 | 검토 신호, 단독 자동 제외 안 함 |
| unchanged_long | 장시간 동일값 지속 | 검토 신호, 단독 자동 제외 안 함 |

- 여러 플래그를 동시에 저장한다. 플래그별 발생 비율 합계는 100%를 넘을 수 있음을 명시한다.
- 정상 판정은 필수 검사에 문제가 없다는 뜻이며 실제 현장값의 정확성을 보장하지 않는다.
- 큰 행사·일괄 출차로 급변할 수 있으므로 급변값을 자동 삭제하지 않는다.
- abrupt_change·unchanged_long의 수치 임계값은 관측 결과를 보고 정한다. 초기에는 변화량과 동일값 지속시간을 측정·보고하되 임의 임계값으로 정상/오류를 확정하지 않는다.
- 잔여면수는 당시 관측한 총면수와 차량수로 계산한다. 총면수 초과를 0대로 잘라 저장하지 않는다.
- 주차장 운영시간 밖의 값도 원본을 보존한다. 운영시간 해석 정책을 정하기 전 이를 자동 오류로 처리하지 않는다.

### FR-11. 기준 변경과 재판정

- 지연·미래 시각 허용 범위는 설정으로 관리한다.
- 기준이 바뀌면 quality_policy_version을 변경한다.
- 재판정은 원본 이력을 수정하지 않고 별도 결과 또는 명시적 재계산 출력으로 제공한다.
- 요약에 사용한 기준 버전을 출력한다. 다른 기준의 분자를 설명 없이 섞지 않는다.

## 9. 수집 상태 요약 요구사항

### FR-12. 조회 인터페이스

- 기본 출력은 CLI 텍스트 요약이다.
- 기계 처리를 위한 JSON 출력을 제공한다.
- 기본 기간은 최근 24시간, 선택 기간은 최근 7일·전체·사용자 지정 시작/종료이다.
- 특정 주차장 ID 필터와 문제 비율·마지막 갱신 시각에 따른 정렬을 제공한다.
- 집계 구간은 시작 포함·종료 제외로 정의한다.
- 조회 시점, 시간대, 기간, 정책 버전, 각 분모를 출력한다.
- 데이터가 없거나 분모가 0이면 N/A 또는 NULL로 표시한다. 0%·100%로 임의 표시하지 않는다.

명령 형태 예시(구현 전 제안):

```text
python -m pubpark.collectors.seoul_history --once
python -m pubpark.reports.collection_status --period 24h
python -m pubpark.reports.collection_status --period 7d --format json
python -m pubpark.reports.collection_status --parking-id 171721 --period all
```

### FR-15. 필수 지표 산식

| 지표 | 분자 | 분모 |

- 주차장 응답률만 높다는 이유로 수집이 안정적이라고 판단하지 않는다. 전체 확보율을 함께 제공한다.
- 과거 운영 중지 기간과 계획 운영 기간을 구분해 각각의 시간을 출력한다.
- 원본 갱신 간격은 중복 제거 후 유효한 원본 시각을 정렬해 계산한다. 수정 관측·시각 누락·역행의 처리 방식을 출력 설명에 명시한다.
- 하루치 데이터를 여러 번 확인한 것을 여러 날의 커버리지로 계산하지 않는다.

## 10. 앱 최신 현황 연동

### FR-16. 호출 경로 전환

- 이력 수집기가 서울시 실시간 API 호출을 담당하고 앱 API는 이력 DB에서 최신 현황을 읽는 구조를 목표로 한다.
- 앱 요청마다 별도 전체 수집을 실행하지 않는다.
- 원본 갱신 시각, 마지막 확인 시각, 품질 상태를 소비자가 구분할 수 있게 제공한다.
- 오래된 값·미연계·초과값은 정상 잔여면수로 제공하지 않는다.
- 최신 유효값이 존재하더라도 더 최근에 미연계·이상 상태가 관측됐다면 과거값을 현재 정상값처럼 숨겨서 반환하지 않는다.
- 수집이 멈추면 API가 응답하더라도 오래된 정보임을 표시한다.
- 초기 이력이 없는 경우 확인 불가와 수집 준비 상태를 반환한다. 가상 0대나 예제 데이터를 실제 모드에 섞지 않는다.
- 기존 앱의 최대 10곳·직선거리 정렬·관광버스 제외와 모의 데이터 모드는 유지한다.
- 정적 월별 갱신, Geocoding, Directions5 호출 주기는 이번 이력 수집 주기와 분리한다.

## 11. 보안·운영·복구 요구사항

### NFR-01. 설정과 보안

- API 키는 backend/.env 또는 실행 환경변수로 읽는다. 환경변수 우선순위를 문서화한다.
- 실제 키·Client Secret·인증 URL은 DB·로그·JSON 요약·테스트 픽스처에 저장하지 않는다.
- DB, WAL/SHM 파일, 로그, 백업은 Git 추적 대상에서 제외한다.
- 테스트는 기본적으로 실제 API를 호출하지 않는다.

### NFR-02. 장애 복구와 운영성

- 정상 종료 시 DB 연결·네트워크 자원·실행 잠금을 해제한다.
- 비정상 종료 후 잠금이 영구적으로 남아 수집을 막지 않아야 한다.
- 로그는 실행 ID, 상태, 건수, 소요 시간, 정규화한 오류를 포함한다.
- 로그가 무제한 증가하지 않도록 순환 설정을 제공한다. 이력 데이터 삭제 정책과 혼동하지 않는다.
- 실행 등록·상태 확인·중지·재개·일회 실행·요약 조회 명령을 문서화한다.
- SQLite 온라인 백업 기능 등 일관된 백업 방법과 복원 확인 절차를 제공한다. WAL 사용 중 DB 본체 파일만 복사하는 것을 정상 백업 절차로 안내하지 않는다.
- 운영 시작 후 1주 동안 DB 증가량과 요약 응답 시간을 측정해 보관·인덱스 정책의 근거로 남긴다.

## 12. 분석 대상 선정 정책

- 첫 1주는 실행 안정성·응답 구조·품질 확인에 사용한다.
- 초기 분석용 축적 목표는 최소 4주로 제안한다. 예측 정확도를 보장하는 최소 기간은 아니다.
- 평일·주말·시간대 커버리지, 유효율, 공백 길이, 실제 값 변화, 30분 뒤 정답 확보율을 보고 후보 주차장을 선정한다.
- 초기에는 근거 없는 종합 점수나 자동 합격 기준을 만들지 않는다.
- 모델링에서는 주차장별 시계열을 분리하고 시간순 검증을 적용한다.
- 학습용 보간·리샘플링·표본 선택은 원본 수집과 분리한 후속 파이프라인에서 수행한다.

| AC-01 | 앱 종료 상태에서 주기 수집 | 앱 없이 예정 주기에 실행·저장됨 |
| AC-02 | 동시 실행 요청 | 실제 수집은 하나, 중복 방지 결과 확인 가능 |
| AC-03 | 같은 원본 응답 반복 | 고유 관측 수는 유지, 회차 확인 기록만 증가 |
| AC-04 | 같은 시각·다른 차량수 | 이전 값과 수정 관측 모두 보존 |
| AC-05 | 값 동일·원본 시각 변경 | 새로운 관측으로 저장 |
| AC-06 | 원본 시각 누락 | 수집 시각으로 대체되지 않고 학습 제외 |
| AC-07 | 미연계·0대 응답 | 정상 빈 주차장으로 처리되지 않음 |
| AC-08 | 차량수 > 총면수 | 원본 보존, 잔여 0대 보정 없음, 초과 플래그 |
| AC-09 | 지연·미래·역행·월/일 경계 | 설정된 시간대·정책대로 판정 |
| AC-10 | 총면수 변경 | 당시 총면수 보존, 과거 잔여면수 불변 |
| AC-11 | 일부 페이지 실패 | 부분 성공 기록, 확보한 관측 보존, 미반환 진단 |
| AC-12 | 인증 오류·429 | 무한 재시도 없음, 구분된 실패 유형 |
| AC-13 | DB 저장 실패 | 회차 성공·저장 완료로 잘못 기록되지 않음 |
| AC-14 | 수집 중 프로세스 종료·재시작 | 중단 실행 식별, 잠금 복구, 기존 이력 유지 |
| AC-15 | 장시간 PC 종료 | 과거값 가짜 생성 없음, 예정 누락 회차 표시 |
| AC-16 | 24시간·7일 요약 | 독립 SQL 집계와 건수·분모·비율 일치 |
| AC-17 | 데이터 없음·분모 0 | N/A/NULL로 표시, 0%·100% 임의 생성 없음 |
| AC-18 | 관광버스 전용·좌표 미확정 | 전자는 제외, 후자는 이력 수집 유지 |
| AC-19 | 수집 중 앱·요약 조회 | 잠금 오류 없이 조회 또는 명시적 재시도 처리 |
| AC-20 | 앱 최신 현황 전환 | 중복 전체 API 호출 없이 최신·품질·지연 상태 제공 |
| AC-21 | 비밀정보 검사 | DB·로그·요약·픽스처에 실제 키 없음 |
| AC-22 | 백업·복원 | 복원 DB의 관측·회차·관계 무결성 확인 |

자동 테스트에는 정상·오류 응답 픽스처, 가짜 시계, 네트워크 모의 응답, 임시 DB를 사용한다. 실제 API 검증은 별도 실행하며 사용한 시점·건수·품질 분포·실패 내역을 기록한다.

## 14. 개발 순서와 산출물

| 단계 | 구현 내용 | 단계 완료 증거 |
| --- | --- | --- |
| 1 | DB 스키마·마이그레이션·저장소 | 중복·수정·롤백·복원 테스트 |
| 2 | 일회 수집·품질 판정 | 정상·부분 실패·이상값 테스트 및 실제 1회 수집 |
| 3 | 5분 일정·동시 실행 방지·복구 | 앱 종료 상태 실행과 중단 후 재시작 검증 |
| 4 | 텍스트·JSON 상태 요약 | 독립 SQL 집계와 일치 |
| 5 | 앱 API의 최신 DB 연동 | 기존 검색·정렬·상태 표시 회귀 테스트 |
| 6 | 초기 운영 관찰 | 24시간 연속 운영 보고, 이후 1주 품질 보고 |

필수 산출물은 구현 코드, DB 스키마·변경 이력, 설정 예제, 수집·요약 CLI, 스케줄 등록/해제 안내, 자동 테스트, 실제 수집 검증 기록, 운영·백업·복구 문서이다.
